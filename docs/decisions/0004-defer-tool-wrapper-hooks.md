# ADR-0004: 推迟工具包装器钩子化

**日期**: 2026-08-30
**状态**: 已采纳（推迟至下个开发周期）

## Problem

`llm_agent.py` 的 `run()` 主循环（约 1700 行）中，干预逻辑（预算升级、反循环提醒、auto-verify 触发、reflection、phase 提示等）硬编码在循环体内，约 18 处干预点。`项目1-设计哲学可实施建议.md` 的 P1-1 建议引入 `pre_execute / post_execute` wrapper 将这些干预外提。

## Decision

**推迟，不做**——至少在当前开发周期内不做。理由：

1. **项目已收敛**：resolved 3/8，367 测试全绿，7 个 war stories。当前阶段是面试准备，`run()` 重构的边际收益远低于"把现有内容讲好"。
2. **干预之间有顺序耦合**：auto-verify 发生在工具批次内循环、预算升级在轮次头部、reflection 可能触发 undo——不是干净的 pre/post 二分，迁移本身是行为级回归。
3. **文档自己也说"新功能开发时顺手做"**——那就等新功能真的来。目前没有新功能计划。
4. **搜索去重已在 executor 层做，证明了"在 executor 内做干预"的可行性**——`ToolExecutor._search_cache` 是 pre-execute 干预的已有先例，新增个别干预不需要 wrapper 抽象。

## Alternatives Considered

1. **现在做轻量 wrapper**: 行为级回归风险 > 可读性收益，且没有新指标验证收益。拒绝。
2. **全量事件总线（pi 风格）**: 已被调研报告否决——项目已收敛，重构超过 2500 行主循环的风险远大于收益。拒绝。

## Risks

- 若未来新增第 4~5 个干预点时，代码膨胀会更严重。缓解：届时再重构，届时干预点样本更多，wrapper 抽象设计更准确。
- 面试时可能被问"为什么不做解耦"——此 ADR 即是回答。

无（推迟决策）
