## 1. 项目定位

### 1.1 一句话版本

> "我做了一个能自主修复真实代码仓库 bug 的 LLM Agent。它不是让模型自由发挥，而是把修复过程拆成六个阶段，用阶段门禁、工具策略、验证质量分层这些**确定性组件**包裹 LLM 的概率性行为——模型负责判断，运行时负责纪律。SWE-bench Lite 官方判定 resolved 4/8，真实 GitHub issue 4/5 修复语义与官方一致。"

### 1.2 一分钟版本（开场白，主动交出节奏）

> "这个项目解决的核心问题是：**LLM agent 什么都能做，但怎么保证它按正确的顺序做正确的事？**
> 我选代码修复作为实验领域，因为成功/失败是客观可测的——测试通过就是修好了，这让 agent 的每个决策都能量化评估。
> 系统把修复拆成理解、复现、定位、补丁、验证、收尾六个阶段。每个阶段有硬性的证据条件：没复现证据不许改代码，没定位候选不许写文件，验证强度不够不许自称成功。这些约束不靠提示词，靠代码物理拦截——模型在错误阶段连写入工具的 schema 都看不到。
> 结果上，SWE-bench Lite 官方 harness 判定 resolved 4/8，五个真实 GitHub issue 修好四个且修复逻辑与官方维护者的 fix 一致。全程 trace 落盘，每一步可审计。"

### 1.3 叙事定位（为什么这个包装对 Agent 岗有效）

面试官对 Agent 岗候选人的核心疑虑是：**"你是调了个 API，还是真的理解 agent 工程？"** 这个包装的每个组件都在回应这个疑虑：

| 简历组件 | 回应的疑虑 |
|---|---|
| 六阶段状态机 + 证据驱动 | 你懂 workflow control，不是无脑 while 循环 |
| 双层门禁（Schema + Policy） | 你懂 tool use 的工程约束，知道提示词不可靠 |
| 确定性反思（零 LLM） | 你懂"什么该交给模型、什么不该"的边界判断 |
| 验证质量分层 | 你懂 agent 的可信性问题（防假成功），这是业务落地的核心关切 |
| token 锚点压缩 + frozen set | 你懂上下文工程和评测方法论，不是跑通就完事 |

**架构哲学一句话**（贯穿全部四条 bullet，面试至少要说一次）：

> "用确定性组件包裹概率性组件。LLM 负责它擅长的——读代码、理解语义、生成补丁；运行时负责它擅长的——纪律、校验、审计。任何 LLM 的输出都要过确定性关卡才能变成系统行为。"

## 2. 项目概述逐句解剖

### 简历原文

> 面向真实代码仓库的 LLM Coding Agent，将 bug 修复拆解为 Understand → Reproduce → Localize → Patch → Verify → Final 六阶段，通过 Phase Gate、Tool Policy、Verification Quality Layer 等确定性组件约束 LLM 的开放行为，确保每步操作有据可依、结果可审计。覆盖 132 条 semi-real issue 与 10 个 SWE-bench Lite 任务，**官方判定 resolved 4/8**，真实 GitHub issue **4/5 修复语义与官方 fix commit 一致**，374 条回归测试全覆盖。

### 逐句拆解

#### 句 1：「面向真实代码仓库的 LLM Coding Agent」

- **代码事实**：agent 的输入是任务定义（issue 标题 + 描述 + 测试命令 + 仓库路径），运行时先把源仓库复制到隔离 workspace（排除缓存目录），agent 在副本里操作，每次写入自动 git commit，可 undo。支持两类任务源：semi-real 提炼任务和 SWE-bench Lite 官方实例。
- **为什么这么写**：区别于"玩具 demo"。"真实"体现在三处——真实 issue 文本、真实开源仓库（tomlkit/packaging/click 等）、官方 harness 判定。
- **追问预演**："真实到什么程度？" → 答：最真实的一档是拿完整开源仓库 + 真实 issue 文本跑，官方 fix commit 对 agent 不可见，修完后人工对比语义。

#### 句 2：「将 bug 修复拆解为 Understand → Reproduce → Localize → Patch → Verify → Final 六阶段」

- **代码事实**：agent 状态里有一个阶段字段，取值就是这六个。阶段不是提示词里的约定，而是**状态机**——工具可见性、写入权限、验证要求全部挂在阶段上。
- **为什么是这六个**：对应人类工程师修 bug 的认知流程。每个阶段有明确的"出口证据"：复现阶段出口是测试失败签名，定位阶段出口是候选文件列表非空，补丁阶段出口是文件修改，验证阶段出口是测试通过。
- **关键设计（面试必说）**：**证据驱动流转，不是时间驱动、更不是模型自报**。每次工具执行完，系统自动检查客观条件——条件满足就自动推进到下一阶段，模型说"我已经理解了"没有用；反过来条件不满足，模型再着急也留在当前阶段。
- **追问预演**："阶段推进谁决定的？" → "系统决定。转移函数的输入是工具执行结果，输出是下一阶段。模型唯一能做的是产生证据。"

#### 句 3：「通过 Phase Gate、Tool Policy、Verification Quality Layer 等确定性组件约束 LLM 的开放行为」

- **代码事实**：三大组件各有明确分工：
  - **Phase Gate（阶段门禁）**：决定"现在处于什么阶段、进下一阶段需要什么证据"；
  - **Tool Policy（工具策略）**：决定"当前阶段哪些工具可用、哪些调用直接物理拦截"；
  - **Verification Quality Layer（验证质量层）**：决定"这次成功的证据强度够不够、不够就降级"。
- **"确定性"的准确含义**：同样输入永远产生同样输出，判定过程零 LLM 参与。对比提示词约束——"请先复现再改代码"是概率性建议，模型可以无视；工具策略是物理事实，模型连工具都看不到。
- **面试金句**："这不是'信任模型'和'不信任模型'的区别，是代码规范和类型系统的区别。规范说'不要用未初始化的变量'，类型系统让这种代码编译不过。我在给 agent 做 type system。"

#### 句 4：「确保每步操作有据可依、结果可审计」

- **代码事实**：trace 里每个工具调用步骤都带证据 ID（如"run_tests:reproduce:exit_1"、"read_file:某文件"、"patch:某文件"），加上阶段快照、验证强度、token 消耗。每次 run 落盘四件套：trace.json（全量步骤）、result.json（最终状态+验证证据+验收报告）、patch.diff（实际改动）、summary.md（人类可读总结）。
- **"可审计"的准确含义**：第三方拿到这四个文件 + 任务定义，**不需要信任我**，可以独立复现判断 agent 每一步做了什么、结论是否站得住。

#### 句 5：「覆盖 132 条 semi-real issue 与 10 个 SWE-bench Lite 任务」

- **代码事实**：semi-real 任务 = 从真实 GitHub issue 提炼的最小复现场景（保留核心逻辑和失败测试，剥离环境依赖），覆盖 9 个开源库（rich/jinja/click/jsonschema/packaging/tomlkit/watchfiles/anyio/dateutil）。SWE-bench Lite 是官方数据集里挑的 10 条实例。
- **两者分工（面试必说）**：semi-real 用于**高频迭代**（跑一次几分钟，每次改代码后跑）；SWE-bench 用于**里程碑验证**（官方 Docker harness，小时级，只在关键节点跑）。
- **⚠️ 口径提示**：简历写 132（README 口径），当前仓库实际已有 136 条任务文件。面试说 132 没问题（这是冻结统计口径），若面试官现场数仓库，解释"后续又补了几条，简历沿用立项时的统计口径"。

#### 句 6：「官方判定 resolved 4/8」

- **代码事实**：10 条 SWE-bench Lite 任务中，2 条 agent 未产出 patch（未提交官方评测），8 条提交官方 Docker harness，4 条 resolved。resolved 的官方定义：容器内 FAIL_TO_PASS 测试全部转通过 **且** PASS_TO_PASS 零回归。
- **为什么写 4/8 而不是 4/10**：诚实口径——只对提交了的负责。但面试要主动讲清楚分母，否则显得回避。
- **翻盘故事（高价值弹药）**：pydicom-1139 首跑 unresolved，逐条归因发现**两个独立根因**：① patch 真实缺陷（迭代器协议语义与官方 gold patch 不同）；② 环境漂移（官方镜像重建时装了 pytest 8，移除了 nose 支持，与 patch 零因果——决定性验证：容器内不打 patch 跑同样测试，同样失败）。修 patch + 锁 pytest 版本后重跑：F2P 3/3 + P2P 38/38 零回归，resolved。**教训：本地通过 ≠ 官方 resolved，每个失败都要拆到根因。**

#### 句 7：「真实 GitHub issue 4/5 修复语义与官方 fix commit 一致」

- **代码事实**：5 个真实 issue 实验——tomlkit#411（嵌套 dotted table）、tomlkit#377（super table 空父头）、packaging#938（extra marker 误解析）、click#3449（CliRunner closed file flush）成功；tomlkit#381 失败（两次 run 都在 parser 侧探索，而官方修复在渲染侧——定位策略缺陷，不是预算不足）。
- **"语义一致"的口径（面试必被追问）**：官方维护者后来提交的 fix commit 对 agent 不可见；agent 修完后，我人工对比修复逻辑是否同构（比如 click#3449：官方在 finally 块给 flush 加了 try/except 保护，agent 的 patch 做了同构修改）。**这是人工判定口径，没有自动化**——主动承认这一点反而加分。
- **回归验证**：修复后跑目标库全量测试——tomlkit 858 passed、packaging 26,952 passed 零回归、click 相关测试全过。

#### 句 8：「374 条回归测试全覆盖」

- **⚠️ 口径提示**：简历/README 写 374，当前仓库实测 **382 passed**（我跑过全量验证）。面试安全说法："简历写作时点 374，现在 382，一直在涨。"千万别说"正好 374"。
- **覆盖层次**：组件级单测（策略、反思器、验证分层、工具）+ 工具端到端。与 frozen set 的分工：单测覆盖组件，frozen set 覆盖端到端行为。

## 3. Bullet ① 双层门禁（Phase Gate & Tool Policy）

### 简历原文

> **双层门禁（Phase Gate & Tool Policy）：**设计六阶段状态机，证据驱动流转——无复现证据禁止进 PATCH、无定位候选禁止写文件；Schema 层按阶段裁剪工具暴露（**Token -39%**），Policy 层四道规则物理拦截违规调用；引入预算硬约束，轮次超限零写入时强制收窄工具列表，从提示式告警升级为物理阻断。

### 这条 bullet 的本质

回答的问题是：**"怎么让 LLM 在正确的时机做正确的事？"** 答案分三层递进：阶段状态机（什么时候）→ 双层工具管控（能用什么）→ 预算硬约束（拖太久怎么办）。三层共同体现"确定性包裹概率性"。

### 逐短语解剖

#### 短语 1：「设计六阶段状态机，证据驱动流转」

**代码事实**（锚点：`app/agent/memory.py` 的阶段字段 + `app/agent/tool_policy.py` 的转移函数）：

- 阶段转移函数在**每次工具执行后**被调用，输入是"哪个工具 + 执行结果"，输出是下一阶段。核心规则：
  - 跑了测试且有失败 → 记录复现证据；已有定位候选 → 推进到 PATCH；
  - 搜索/读文件命中具体文件 → 进入定位候选列表；已有复现证据 → 推进到 PATCH；
  - 写入成功 → 推进到 VERIFY；全量测试通过 → 具备 FINAL 资格。
- **证据的两种硬类型**：
  - **复现证据**：跑过测试命令（失败输出被结构化提取成失败签名）。另有一个"弱静态"变体——任务元数据显式标记"没有可跑测试"的真实仓库任务，允许以静态分析证据进入补丁阶段。
  - **定位候选**：带置信度评分的文件列表。来源有六种：初始排序（issue 文本 + 提示文件）、搜索命中（0.45）、读过该文件（0.5）、测试失败位置直接点名（0.75）、失败后自动引导搜索命中（0.6）、写入时主动声明 override 理由（0.4）。
- **为什么这样设计**：如果靠模型自报"我进入补丁阶段了"，模型会在理解不足时提前动手。证据驱动把"准备好了"变成可验证的布尔条件。

**面试话术**：
> "阶段流转是系统决定的，不是模型决定的。转移条件全是客观证据——跑没跑过测试、候选文件列表是否非空。模型唯一能做的是产生证据，不能跳级。"

#### 短语 2：「无复现证据禁止进 PATCH」

**代码事实**（锚点：`tool_policy.py` 的写入资格判定）：

写入门闩要求**三个条件同时成立**：① 当前处于 PATCH 或 LOCALIZE 阶段；② 有复现证据（或任务显式标记弱静态）；③ 定位候选列表非空。任一不满足，写入工具的调用直接被拦截，模型收到"PATCH gate is closed"的结构化错误。

**为什么复现证据重要**：没有"修复前失败"的证据，就无法区分"我修好了"和"本来就没坏"——这是假成功的主要来源之一。

**边界情况的诚实处理（面试加分点）**：真实仓库常常没有可跑的测试（依赖装不起来）。最初的状态机隐含假设"总有测试可跑"，导致真实仓库任务永远卡在复现阶段死锁。修复方式：复现阶段已有定位候选时，允许**阶段流转**进入 PATCH（让模型看到写工具），但**写入门闩不放松**——弹性在前、底线在后。修死锁不能顺手拆安全机制。

#### 短语 3：「无定位候选禁止写文件」

**代码事实**（锚点：`tool_policy.py` 的写入目标校验）：

- 写入工具的目标文件路径必须在候选列表中，否则拦截。
- **逃生阀设计**：模型可以附带一个"定位豁免理由"（至少 20 个字符的具体证据说明）来改候选外的文件——豁免成功后该文件自动以 0.4 置信度进入候选列表，留下审计痕迹。
- **为什么留逃生阀**：定位候选来自启发式评分，可能漏掉真正的修复点（比如修复点在测试文件里）。完全堵死会让 agent 在"正确的修复"面前无能为力。关键是豁免要**留痕**——事后审计能看到"模型为什么改了这个没被推荐的文件"。

**面试话术**：
> "门禁不是铁板一块，是'默认拦截 + 留痕豁免'。模型可以改候选外的文件，但必须写出具体理由，理由和这次写入一起进 trace。这保留了处理长尾情况的能力，又不放弃审计。"

#### 短语 4：「Schema 层按阶段裁剪工具暴露（Token -39%）」

**代码事实**（锚点：`app/agent/tool_router.py`）：

- 全部 11 个工具（列目录/图搜索/代码搜索/正则搜索/读文件/跑测试/受控求值/写文件/编辑文件/看差异/回滚）定义在单一数据源里，每个工具带"是否只读""是否并发安全"属性。
- 每轮调用 LLM 前，按当前阶段 + 状态动态过滤工具 schema：理解阶段看不到任何写入工具（只有浏览、搜索、读文件和跑测试）；补丁阶段才看到写入工具；还没写过文件时连"回滚"都不出现；验证阶段有未确认的改动时"跑测试"被暂时隐藏（强制先看 diff）。
- **数字来源**：task_010 单任务对照实验——baseline 暴露全部工具 30,510 tokens / 7 次调用；按阶段裁剪后 18,553 tokens / 5 次调用，**-39%**，任务结果相同。

**为什么 Schema 层和 Policy 层要分开做（双层的原因）**：
- Schema 裁剪是**前置引导**——模型看不到工具就不会尝试调用，还省了每轮的 schema token 开销；
- Policy 拦截是**后置兜底**——有些状态是动态的（比如补丁恢复状态要临时加回写工具），schema 过滤覆盖不了所有时序，策略层在调用时刻做最终裁决。
- 两层缺一不可：只有 Schema 层，动态状态会漏；只有 Policy 层，模型会反复尝试被禁工具浪费轮次。

**⚠️ 诚实边界（面试官大概率追问，这是埋好的"示弱点"）**：
> "-39% 是单任务数字。我后来扩展到 5 个任务验证，发现 2/5 的 token 反而上升了——规律是反升的两个恰好多了一轮 LLM 调用。省 schema 是小头（每轮固定 3-5K），多一轮完整上下文重发是大头（15-50K）。这个发现让我把优化方向从'省 schema'转向'省轮次'——就是第二条 bullet 的自动验证。"

这个"主动示弱"是设计好的叙事钩子：它证明你懂"单任务验证会骗人"，并自然引出 bullet ②。

#### 短语 5：「Policy 层四道规则物理拦截违规调用」

**代码事实**（锚点：`tool_policy.py` 的校验函数，按顺序执行）：

| # | 规则 | 防什么 |
|---|---|---|
| ① | 阶段白名单 | 当前阶段不该用的工具（理解阶段调写入） |
| ② | PATCH 门闩 | 没复现证据/没候选就要写文件 |
| ③ | 写入目标校验 | 改没分析过的文件（无豁免理由） |
| ④ | diff-before-tests | 改完文件没看 diff 就跑测试 |

**第四道规则值得单独讲（面试亮点）**：系统维护两个计数器——工作区写入次数和 diff 观察次数。每次写入 +1，每次看 diff 把观察次数对齐到当前写入次数。**两者不相等时禁止跑测试**。堵死的时序漏洞是："改文件 → 直接跑测试 → 通过 → 自称成功"，中间跳过了"确认自己改了什么"。这是从分布式系统的版本号校验借来的思路——不需要 LLM 记住"我改完还没看 diff"，代码替它记住。

**物理拦截的含义**：被拦截的调用不会执行，模型收到结构化的"工具策略阻止"结果，附带原因说明。模型下一步只能换合法路径。

**如果追问"还有别的规则吗"**：还有第五道——图搜索工具单次 run 限 3 次（防止在图查询上空转），以及预算收窄（见下）。简历写"四道"是因为这四道是核心写入安全链。

#### 短语 6：「引入预算硬约束，轮次超限零写入时强制收窄工具列表」

**代码事实**（锚点：`llm_agent.py` 主循环的预算升级逻辑 + `tool_policy.py` 的收窄集合）：

- **触发条件**：轮次达到上限的 75% 且一次都没写入过（阈值下限为 2，保证第一轮永远有完整探索机会）。
- **动作（三件套）**：① 状态标记激活；② Schema 层把工具列表**替换**为收窄集合（编辑/写入/跑测试/看差异/受控求值，共 5 个）——探索工具从模型视野物理消失；③ Policy 层拦截收窄集合之外的一切调用。
- **收窄集合为什么保留"受控求值"**：它是验证工具而非探索工具——issue 自带复现脚本时，用它执行是最短修复路径；且它只允许单表达式求值，无法用于无限探索。（这里还有个修过的 bug：最初收窄集合与补丁阶段默认集合求交集，把受控求值静默挡掉了——后来改为直接替换。）
- **同时注入一条系统消息**：要求模型"① 一句话总结已确认的根因；② 基于已读代码写最小补丁；③ 系统会自动验证"。消息拼接进最后一条 user 消息尾部，不新增独立消息——避免破坏消息配对协议。

#### 短语 7：「从提示式告警升级为物理阻断」

**这是整条 bullet 的叙事高潮，对应 click#3449 五次 run 弧线**（面试最核心的 war story，务必能完整讲）：

| Run | 干预 | 结果 | 告警后行为 |
|---|---|---|---|
| 1 | 无 | incomplete，0 patch | 探索 16 轮耗尽 |
| 2 | 提示式告警 | incomplete，0 patch | **无视提示，继续读** |
| 3 | 硬约束（4 工具） | incomplete，0 patch | 被拦后连续空响应（当时误判"罢工"） |
| 4 | 硬约束 + 受控求值 | incomplete，0 patch | 配合 1 轮 → 读被拦 → 空响应 |
| 5 | 硬约束 + max_tokens 修复 | **success，1 patch** | 4 次读被拦 → 转向跑测试 → 一次编辑成功 → 自动收束 |

- **Run 2 的意义**：证明提示式告警无效——模型收到"请总结并写 patch"的提醒后，行为零变化。这是"提示是概率性建议"的直接实验证据。
- **Run 3/4 的插曲（面试官若深挖必讲）**：空响应不是罢工，是 **reasoning 模型的思考链烧完了 max_tokens 上限**——逐轮 token 分解发现空响应轮的 completion 精确等于 8000（撞线的数学指纹），API 返回的 finish_reason=length 证实截断。当时系统丢弃了 finish_reason 字段，导致"截断"和"主动停止"不可区分。修复：max_tokens 8000→32000 + finish_reason 落 trace。
- **Run 5 的意义**：硬约束真实有效——模型被拦 4 次读之后**自主切换到合法路径**（跑测试建基线 → 编辑 → 验证 → 自动收束），修复语义与 click 8.4.1 官方修复同构。此前硬约束的效果被截断 bug 完全掩盖。
- **一句话总结这个弧线**："提示无效 ≠ 方向不对；表象（空响应）≠ 根因（截断）。五次 run 证明了从'拍脑袋改 prompt'到'观测驱动定位根因'的方法论转变。"

**面试金句**：
> "提示是希望他听话，硬约束是让他只能做对的事。"

## 4. Bullet ② 确定性反思与自动验证

### 简历原文

> **确定性反思与自动验证：**实现 130 行纯函数 Reflector，**零 LLM 调用**完成失败签名对比与 undo/保留决策；写入后 Runtime 自动执行三级验证链（show\_diff → targeted tests → full tests），结果同轮回喂，消除验证决策的额外 LLM 轮次（**5 任务平均 Token -27.4%**）。

### 这条 bullet 的本质

回答两个问题：**"patch 失败后下一步怎么决策？"**（反思器——不交给 LLM）和 **"怎么省 LLM 轮次？"**（自动验证——确定性流程下沉到运行时）。两者共同的哲学：**决策空间小的事情，if-else 优于调 LLM**。

### 逐短语解剖

#### 短语 1：「实现 130 行纯函数 Reflector」

- **代码事实**（锚点：`app/agent/reflector.py`）：实际 **123 行**（含注释）。面试说"约 130 行"或"123 行"都行，别说死"正好 130"。
- **"纯函数"的准确含义**：无 LLM 调用、无 I/O、无隐藏状态。输入是（agent 状态、修复前失败签名、修复后失败签名、改动文件列表、补丁文件数上限），输出是一个结构化决策（失败变化类型 + 可能原因 + 下一阶段 + 必要动作 + 是否回滚）。
- **为什么这么小**：因为决策空间只有 5 种情况（见下），所有判断都是确定性运算——哈希比较、集合运算、数值比较。没有一行需要"理解"。

#### 短语 2：「零 LLM 调用完成失败签名对比与 undo/保留决策」

**失败签名是什么**（锚点：`memory.py` 的签名结构）：

把 run_tests 结构化提取的失败信息（失败测试列表、断言行、失败位置）序列化后取 SHA-256 哈希的前 16 位。**签名的意义**：把"失败长什么样"压缩成一个可比较的指纹。

**五分支决策树**（反思器的全部逻辑，面试要能背）：

| 条件 | 判定 | 动作 |
|---|---|---|
| 改了候选列表之外的文件 | wrong_file | 回滚（若签名不变）+ 回定位 |
| 改动文件的最高置信度 < 0.4 | low_confidence | 回滚（若签名不变）+ 回定位 |
| 改动文件数超过上限 | overfit | 回滚（若签名不变）+ 回定位 |
| 失败签名**不变** | wrong_hypothesis | **不回滚** + 回定位 |
| 失败签名**变化** | partial_fix | **不回滚** + 留在补丁阶段继续 |

**最关键的设计判断（面试必讲）**：签名变化但没完全修好时**不回滚**——签名变化意味着补丁至少改变了某些测试的行为，方向是对的，应该保留有用部分继续修。签名不变才是"改了个寂寞"。**这个区分如果交给 LLM，它很可能把两种情况都判成"失败，重来"**——因为从模型视角两者都是"测试还是挂"。

**为什么不用 LLM 做反思（高概率追问）**：

> "业界常见做法是把反思写成 prompt：'你的 patch 测试失败了，请分析原因决定下一步'。这有三个问题：**不可测试**（同输入可能返回不同决策，没法写单测）、**不可审计**（不知道模型为什么这么决定）、**烧 token**（又是一次完整上下文重发）。而反思的决策空间其实只有 5 种情况——当你发现决策空间这么小的时候，写 if-else 是比调 LLM 更好的方案。"

**undo 怎么实现**（可能追问）：每次写入成功后运行时自动做一次 git commit（隔离 workspace 内），undo 就是回滚最近一次 commit。所以回滚是原子的、可靠的，不依赖模型自己"改回去"。

#### 短语 3：「写入后 Runtime 自动执行三级验证链（show_diff → targeted tests → full tests）」

**代码事实**（锚点：`llm_agent.py` 主循环的"立即自动验证"流程）：

- **触发**：write_file/edit_file 成功，且当前改动代次还没被验证过。
- **三级串行执行，全部由运行时代劳**：
  1. **show_diff**：查看当前工作区相对原始仓库的全部改动（同时把"diff 已观察"对齐到当前写入代次——满足第四道门禁）；
  2. **targeted tests**：从最近一次失败摘要里提取 pytest 节点 ID（最多 3 个），只重跑失败过的测试——快，先给模型一个早期信号；
  3. **full tests**：跑任务自带的完整测试命令。
- **结果同轮回喂**：三级结果 + （若失败的）反思决策打包成一条消息，追加在本次工具结果后面喂给模型。模型下一轮醒来时，验证已经做完了。
- **失败时的附加动作**：自动触发反思器 → 若判定回滚则自动执行 undo → 回滚结果也附在同一条消息里。

**targeted 命令怎么构造**（细节追问）：从失败摘要的"失败测试"字段里用正则提取 `文件.py::类::方法` 形式的节点 ID，拼到原测试命令前缀后面。最多取 3 个，防止命令过长。

#### 短语 4：「结果同轮回喂，消除验证决策的额外 LLM 轮次（5 任务平均 Token -27.4%）」

**旧流程 vs 新流程（面试画图讲）**：

```
旧：写入 → [LLM轮] 决定看diff → [LLM轮] 决定跑targeted → [LLM轮] 决定跑full
     每一轮都重发 system prompt + 工具 schema + 全部历史
新：写入 → runtime 串完三级 → 一条消息回喂（0 个额外 LLM 轮）
```

- **数字来源**：同一批 5 个任务、同一模型、只改策略参数的对照实验——自动验证版本相比 baseline 平均 **-27.4%** token，且**无任务反升**（对比 schema 裁剪的 2/5 反升）。
- **与 -39% 的关系（必考）**：-39% 是"省 schema"（每轮固定开销，小头），-27.4% 是"省轮次"（每省一轮省一次全量上下文重发，大头）。后者更稳定、上限更高。
- **配套机制 auto_finalize**（可提）：diff 已观察 + 全量验证通过 + 无待验证改动 → 系统直接退出循环收尾，连"模型确认成功"的那一轮都省了。模型甚至不需要说"我修好了"——证据已经齐了。

**追问预演**："自动验证会不会剥夺模型的判断？" → "不会剥夺，只是前置。验证结果回喂后，模型依然可以基于结果做任何决策——继续修、读文件、或收尾。被消除的只是'决定要不要验证'这个本身没有判断含量的轮次。"

## 5. Bullet ③ 验证质量分层

### 简历原文

> **验证质量分层：**构建四级验证强度体系（Missing / Weak / Local Smoke / Full Verification），模型自称成功但证据不足时 **系统强制降级**——验证结论由代码判定，非模型自报，防止 Agent 将弱验证包装为可信成功。

### 这条 bullet 的本质

回答的问题是：**"agent 说'我修好了'，你敢信吗？"** 这是 agent 业务落地的第一关切——一个会把失败包装成成功的 agent 没有商业价值。答案：验证结论的判定权从模型手里收走，交给代码；证据强度不够就强制降级，宁可诚实失败。

### 逐短语解剖

#### 短语 1：「构建四级验证强度体系（Missing / Weak / Local Smoke / Full Verification）」

**代码事实**（锚点：`memory.py` 的强度枚举 + `verification.py` 的升级函数 + `verifier.py` 的判定报告）：

代码里实际是**两层结构**，面试要能分开讲：

- **第一层·验证强度**（"跑了什么测试"）：none / weak / targeted / full 四级。对应简历的 Missing / Weak / (targeted) / Full。
  - 初始强度从任务元数据推断（任务标记弱验证或测试命令是兜底命令 → 初始 weak）；
  - 每次测试运行后按结果**累积升级**：退出码 0 且已有改动 → full；只跑了部分 → targeted；兜底命令跑的 → 封顶 weak。
- **第二层·验证判定**（"这个成功可信吗"）：验证器综合强度 + 补丁 + 前后测试退出码 + 是否官方口径，输出结构化报告（验证级别 / 风险等级 / 证据质量 / 缺失证据清单 / 是否接受）。
- **简历里 Local Smoke 的准确位置**：特指 SWE-bench 类任务**本地全量测试通过但未经官方 harness** 的情形——系统自动把这种"成功"降级标记为 local_smoke_success，风险中等，**不接受为最终成功**，并附建议"用官方 harness 评测导出的 prediction"。

**四级对照表（面试直接用）**：

| 级别 | 条件 | 含义 |
|---|---|---|
| Missing | 无 patch 或无任何测试证据 | 直接拒绝 |
| Weak | 仅静态分析 / 兜底测试命令 | 不可接受 |
| Local Smoke | 本地全量测试过，但非官方口径 | 可信但明确标注"不等于官方通过" |
| Full Verification | 修复前有失败证据 + 修复后全量通过 | 最强证据，唯一可接受为 success |

#### 短语 2：「模型自称成功但证据不足时系统强制降级」

**代码事实**（锚点：`verification.py` 的最终状态调整函数）：

- 最终状态分类函数先按客观条件判定：success 需要 **补丁存在 + 最后测试退出码 0 + 已验证代次 == 当前写入代次**（代数校验，防"改完没重验"）。
- 然后验证强度调整函数做**强制降级**：
  - 模型路径判定 success 但强度只有 weak/targeted 且有补丁 → 降级为 `success_weak_verification`（弱验证成功，验收报告标"不接受"）；
  - 强度 none → 直接降为 incomplete。
- **反向降级也存在**：模型自称"未完成"（文本里出现"无法完成"等标记）→ 强制 incomplete，即使测试全过。模型的自述**双向**都不影响判定，只作参考。

**pydicom-1139 案例（这条 bullet 的实证弹药）**：

> "本地容器里同一批测试全过，agent 认为修好了。但官方 Docker harness 判 unresolved。逐条归因发现两个独立根因：patch 的迭代器协议语义与官方 gold patch 不同（真缺陷）+ 官方镜像重建时装了 pytest 8 移除了 nose 支持（环境问题，与 patch 零因果——容器内不打 patch 跑同样测试也挂，这是决定性验证）。修 patch + 锁环境后重跑，F2P 3/3 + P2P 38/38。这个案例验证了分层的价值：**本地通过和官方通过是两个口径，系统必须能区分，而不是靠人的诚信。**"

#### 短语 3：「验证结论由代码判定，非模型自报」

- **判定的全部输入是客观量**：退出码、写入代次计数、diff 观察代次、补丁是否存在、任务元数据。没有一个字来自模型的自我评价。
- **模型自报的两个典型失效模式**（面试可举）：
  1. 模型看到 targeted 测试过了就自称成功（没跑全量）；
  2. "本来就没坏"——模型改了个无关文件，测试本来就过，自称修复成功。四级体系要求"修复前失败证据 + 修复后通过"**同时成立**，两个都堵死。
- **边界案例佐证**：有个任务（rich#2411）测试一开始就是通过的，agent 没有产出 patch，最终状态保持 incomplete 而不是 success——系统拒绝把"没坏"报告成"修好了"。

#### 短语 4：「防止 Agent 将弱验证包装为可信成功」

- **为什么这是行业问题**（面试官可能问"这是你发明的还是行业共识"）：读 SWE-bench 相关评测报告时的常见模式——很多系统把"本地测试通过"报告为 resolved，官方 harness 重跑通不过。不是作弊，是**验证口径不一致**。我的做法是把它制度化：验证级别、证据质量、缺失证据清单全部结构化落盘，第三方不需要信任我，自己看字段。
- **产品视角收尾**（对 agent 岗加分）："这套东西的本质是给 agent 的输出做'质检分级'——业务方拿到的不是一个布尔值，是带证据链的置信度分层。弱验证的结果不是被丢弃，是被标记后降级交付，人可以决定要不要补验证。"

## 6. Bullet ④ 上下文工程与评测体系

### 简历原文

> **上下文工程与评测体系：**以 API 实测 token 用量为锚点驱动上下文压缩判定，替代静态字符阈值，校准后同等任务零错误压缩；测试失败信息结构化提取（断言位置 / 异常类型 / 符号名），无需模型读取完整日志即可定位根因。frozen\_40 连续 **72+ 策略版本零回归**，全部运行证据随仓库分发、逐条可审计。

### 这条 bullet 的本质

两个独立能力打包：**上下文工程**（token 锚点压缩 + 失败信息结构化提取——"喂给模型什么"）和**评测方法论**（frozen set 回归门禁——"怎么证明没改坏"）。前者是省 token 和保信息密度，后者是工程纪律。

### 逐短语解剖

#### 短语 1：「以 API 实测 token 用量为锚点驱动上下文压缩判定，替代静态字符阈值」

**代码事实**（锚点：`llm_agent.py` 的上下文估算与压缩函数）：

- **旧方案**：消息历史字符数超过固定阈值（80K 字符）就触发压缩——把中间轮次摘要成 system 消息，只保留首条任务输入 + 最近 3 轮。
- **新方案**：判定改为"估算 token 数 > 模型窗口 − 预留量"。估算优先用**最近一次 API 返回的 prompt_tokens 实测值做锚点**（天然覆盖 system prompt + 工具 schema 开销，比任何离线估算准）；无锚点时（首次调用前）退回"字符数 ÷ 2.5"保守估算——高估 token → 提前压缩 → 安全方向。
- **配置分工**：窗口大小进环境变量（模型属性，随模型切换），预留量进策略文件（行为参数）。

**为什么必须换（War Story 9，度量推翻直觉的典型案例）**：

> "80K 字符阈值是 6 月 15 日定的，两个月从没验证过。8 月底我建了观测管道——保留 API 返回的 prompt_tokens（之前只留 total 就丢弃），每个响应步骤记录字符估算与实测对照。跑了 3 个任务 46 次调用，拿到两个事实：
> ① 稳态字符/token 比值 2.45（范围 1.93~3.10）——字符估算本身偏差 ±24%；
> ② 我用的模型窗口是 **1M token**，不是我以为的 64K。80K 字符 ≈ 37K token ≈ 窗口的 **3.7%**。
> 结论是颠覆性的：**压缩在长任务里从来都不必要**——每次压缩都在丢不该丢的上下文（PATCH 阶段的失败签名和定位历史），纯粹被一个从未校准的阈值人为触发。"

**面试金句**："拍脑袋的阈值不会自己变对，观测才会告诉你真相。"

#### 短语 2：「校准后同等任务零错误压缩」

- **验证方式**：重跑一个旧逻辑必触发压缩的任务（marshmallow_1343）——旧方案压缩 1 次，新方案 **0 次**，上下文全程 38.5K tokens（窗口 3.9%），PATCH 阶段历史完整保留到任务结束。
- **"零错误压缩"的准确含义**：不是"零压缩"（极端长任务该压还是会压），是"不再发生不该压的压缩"——判定基于真实占用而非拍脑袋阈值。
- **压缩本身的工程细节（若被追问"压缩怎么做的"）**：
  - 保留首条任务输入 + 最近 3 轮，中间轮次摘要成 system 消息（每条压到 300 字符以内）；
  - **配对保护**：压缩边界不能切在"assistant 工具调用"和它的"工具结果"之间——否则保留的 tool_result 前面没有配对的 tool_calls，严格校验的 API 直接报 400。边界落在配对中间时向后回退。这是踩过坑后加的不变量（War Story 8 的 Bug 2）。
  - 另有一层"微压缩"：单条超大工具结果在进入历史前先截断（阈值 ×2），防止一条消息撑爆上下文。

#### 短语 3：「测试失败信息结构化提取（断言位置 / 异常类型 / 符号名），无需模型读取完整日志即可定位根因」

**代码事实**（锚点：`app/tools/run_tests.py` 的失败摘要构建）：

- pytest 输出可能是几百上千行，模型根本看不完。run_tests 工具在返回前用正则解析输出，提取五类结构化信息：
  1. **失败测试列表**（FAILED 行）；
  2. **断言位置**（文件:行号 + 错误描述）；
  3. **断言内容**（assert 语句原文）；
  4. **异常类型和消息**（取最后一个 traceback 异常）；
  5. **可能相关的符号名**（从异常消息里提取引号包裹的标识符和大写开头的类名，最多 8 个）。
- 再拼一条 500 字符以内的中文短摘要（"断言: … 位置: … 失败测试: … 异常: … 相关符号: …"）。
- **配套的自动引导搜索**（加分细节）：失败摘要里没有位置信息但有符号名时，系统自动用符号名发起代码搜索，把命中文件直接补进定位候选列表（置信度 0.6）——模型还没开口，定位信号已经喂到嘴边。
- **另一个细节**：测试命令自动追加 pytest 短输出 flags（短 traceback、去头、去警告），从源头压缩输出量。

**设计思想（面试话术）**：
> "这是'在工具层解决问题'的思路——不是让模型更聪明地读日志，是让工具返回的信息更精准。模型拿到的是'哪个测试挂了、在哪一行挂的、什么异常、和哪些符号有关'，它下一步直接就是搜索/读那个位置，跳过了'从几百行输出里找重点'这个低价值环节。"

**实证支撑**（War Story 14 的审计结论，若被追问"你怎么知道信息够用"）："我扫过全部历史 trace：61 次测试失败后，0 次同命令重跑、0 次搜索惯性——模型看完失败摘要直接行动。摘要截断标记出现 0 次。这说明结构化提取的信息密度是足够的。"

#### 短语 4：「frozen_40 连续 72+ 策略版本零回归」

**代码事实**（锚点：`benchmarks/manifests/real_issue_tasks_frozen_40_v1.json` + `evals/` 评测管道）：

- **frozen set 是什么**：从 semi-real 任务里冻结的固定评测集（40 条为主力，另有 15/18/20 条分层）。**只增不减、永不修改**——新增任务可以加入，但不替换已有任务。清单以 manifest 文件形式固化在仓库里。
- **回归门禁流程**：每次改策略或 agent 逻辑 → 同一份 frozen set 全量重跑 → 结果 diff → 新增失败 = 回归 → 回归必须修复或记录为 known regression（写明根因和时间）。
- **72+ 的含义**：连续 72+ 个策略版本跑下来零回归。这是"数据结构化的纪律"——不靠记忆判断"这次改动应该不影响之前的任务"，靠自动化回归每次告诉你。
- **两层测试的分工（必考）**：374/382 条 pytest 单测覆盖**组件级**（策略、反思器、验证分层、工具）；frozen set 覆盖**端到端行为级**。单测全绿但端到端回归的情况真实存在（War Story 5：签名说可选、实现说必填的参数 bug，单测没拦住）。

**追问预演**："frozen set 和 SWE-bench 什么关系？" → "内部迭代用 frozen set（分钟级，高频）；对外可比用 SWE-bench 官方 harness（小时级，里程碑）。一个保证'没改坏'，一个证明'真的行'。"

#### 短语 5：「全部运行证据随仓库分发、逐条可审计」

- **代码事实**：`evidence/` 目录随仓库分发——13 个代表性 run 的四件套（trace/result/patch/summary）、5 个真实 issue 的完整产物、SWE-bench 官方评测的全部报告（含翻盘重跑的官方汇总）。
- **审计的含义再强调**：验证级别、证据质量、缺失证据清单都是结构化字段——第三方不需要信任我的叙述，直接读字段。
- **面试话术**："agent 系统最大的信任问题是'你说修好了，凭什么'。我的答案是让证据自己说话——每个结论旁边都挂着它的证据链，缺什么证据字段里写着。"

## 8. 高危追问与防御（按概率排序）

### 8.1 「你这个项目和 Cursor / Copilot 什么区别？」（几乎必问）

> "Cursor 是辅助人写代码——人在环上，每一步人确认。我做的是 autonomous agent——issue 进、patch 出，全程无人干预。这带来完全不同的工程问题：Cursor 只需要好用，我的系统还需要**可信**——没人看着的时候，怎么保证它不跳过复现直接改代码、不把弱验证包装成成功。所以我的核心工作量都在行为约束和验证分层上，而不是代码生成质量上。"

### 8.2 「为什么不用 LangChain / LangGraph？」（Agent 岗必问）

> "三个原因。① 我要解决的核心问题是**行为约束**，不是编排——LangGraph 解决的是'流程怎么组织'，我的问题 是'流程中的每一步怎么保证不被模型绕过'，这需要直接控制工具暴露和调用拦截，框架的抽象层反而是障碍。② 调试所有权：出问题时我需要逐轮看消息序列、token 分解、finish_reason——这些在框架里被抽象掉了，我自己写循环每个字段都在我手里（max_tokens 截断那个 bug 就是靠逐轮 token 分解定位的，隔一层框架可能就找不到了）。③ 规模匹配：核心循环两千多行，引入图编排引擎是杀鸡用牛刀。框架适合快速搭原型，我这个项目本身就是研究 agent 行为控制，自己写就是最好的学习。"

### 8.3 「主循环文件两千多行为什么不拆？」（看过代码的面试官会问）

> "有意识的设计决策。主循环里有十几处干预点——预算升级注入、自动验证回喂、反思触发、阶段推进、上下文压缩——它们之间有严格的执行顺序依赖。拆成多个文件会让顺序依赖变成隐式的状态传递，改代码时容易破坏顺序。两千多行在一个文件里不漂亮，但顺序是正确的。而且项目已收敛，收敛期做大规模重构的风险不可接受。不是没时间拆，是选择不拆。"

### 8.4 「Agentic 体现在哪里？」（概念型面试官）

三层次回答：
> "① **自主决策**：132 个任务每个的执行路径都不同——先跑测试还是先搜索、改一个文件还是两个、失败后回滚还是保留，都是 agent 基于证据自己决定的，没有预设剧本。
> ② **感知-行动闭环**：结构化的 agent 状态（阶段、失败签名、候选列表）不是记录用的，是**反向约束行为**的——状态决定工具可见性和写入权限。感知改变行动。
> ③ **失败恢复**：patch 失败后自动反思、必要时自动回滚、回退到定位阶段重新来——不是失败就终止，是失败后自主调整策略。"

### 8.5 「4/8 这个数字不高啊，SOTA 都 40%+ 了」（压力测试）

> "对，我主动承认这是小样本 + 非主力调优方向的结果。10 条里 2 条没产出 patch（一条被反思器判 wrong_file 回滚三次，一条 16 轮全在读代码），提交的 8 条里 4 条 resolved。这个项目的重心不在刷 SWE-bench 分数，而在**行为可控性和结果可信性**——比如 pydicom-1139 那次，本地全过但官方判 unresolved，我的系统能把两个独立根因（patch 缺陷 + 环境漂移）拆开归因，这比分数更能说明系统质量。如果要把分数做上去，路径也清楚：定位策略改进（#381 那种 parser/渲染侧定位错误）+ 更多失败测试锚点的任务筛选。"

### 8.6 「提示词和硬约束，到底哪个有用？」（方法论追问）

> "都有用，但分工不同。提示词塑造**默认行为倾向**——我的 system prompt 里有'编辑是探索工具，错了 undo 成本为零'这类第一性原则引导，消融实验证明它对 token 效率有显著影响（4 个任务里 3 个省 23-51%，最难的 tomlkit_411 是成功/失败的质变）。但提示词**不能做安全边界**——click#3449 的 Run 2 证明模型可以无视任何提醒。所以我的原则是：提示词管效率，硬约束管底线。凡是'违反了会产出不可信结果'的行为（跳过复现、弱验证自称成功），必须硬约束；凡是'做了更好'的行为（少读文件、早进补丁），用提示词引导。"

### 8.7 「你一个人做的？多久？」（真实性核查）

> "三个月左右，从 rule-based solver 起步演进到 LLM agent。前期 rule-based 版本帮我理解了修复流程的本质（哪些步骤需要判断、哪些是确定性流程），后来发现 bug 修复的核心判断（读代码、理解语义、生成补丁）根本无法规则化，才转向 LLM。这个演进路径本身就是收获——我知道哪些环节值得交给模型，因为我试过不交给模型。"

### 8.8 「下一步做什么？」（收尾问题）

> "项目已收敛，但如果继续，三个方向，核心思路是'关闭已知问题'而非加新功能：① 重叠读检测——trace 审计发现 55%+ 的文件读取是重复的，拦截可省 token（搜索类工具已有去重缓存，读文件还没有）；② 定位策略改进——#381 暴露的 parser/渲染侧定位错误说明候选排序对'修复在别处'的情况无能为力；③ 把验证质量分层的输出接到人工复核工作流——弱验证结果降级交付给人决策，这是走向业务化的自然一步。"
