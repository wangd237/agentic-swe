# Tool-Call 设计文档

以当前项目代码（`app/agent/` 与 `app/tools/`）为唯一依据，回答面试中 tool-call 的三个核心问题。

---

## 一、LLM 结构化输出出错怎么办

不依赖 LLM 自觉，四层递进防御。

### 1. JSON 解析兜底

**位置**：`llm_agent.py` → `OpenAICompatibleChatClient._normalize_openai_response()`

```python
try:
    tool_input = json.loads(tool_call.function.arguments or "{}")
except json.JSONDecodeError:
    tool_input = {}
```

工具参数解析失败直接退化为空字典，不会抛异常终止 run。参数缺失会导致工具自身校验报错（如 `required` 字段缺失），错误以结构化 tool_result 回喂模型，模型可自行修正。

### 2. 文本内工具调用恢复

**位置**：`llm_agent.py` → `_recover_text_tool_blocks()`

当 LLM 没有使用 `tool_use` content block、而是在纯文本中写了 JSON 格式的工具调用时：

```python
if assistant_text and not tool_blocks:
    recovered_text_tool_blocks = self._recover_text_tool_blocks(
        text=assistant_text,
        allowed_tool_names=current_tool_names,
        max_blocks=1,
    )
```

用 `json.JSONDecoder().raw_decode()` 扫描文本，只匹配当前阶段允许的合法工具名（`allowed_tool_names` 过滤），最多恢复 1 个（避免误识别）。

### 3. 空响应分类处理

**位置**：`llm_agent.py` 主循环底部

| 场景 | 判断依据 | 处理 |
|------|---------|------|
| 推理链被截断 | `finish_reason == "length"` | 提示"不要展开长推理，直接给结论" |
| 真空响应 | 无 tool_calls 且无 text | 提示"任务未完成，继续" |

两种成因分开处理，因为应对策略相反：截断是资源问题，罢工是行为问题。`max_empty_response_retries` 设上限防止无限重试。

### 4. 工具策略门控（执行前预防）

**位置**：`tool_policy.py` → `ToolPolicy.validate()`

在工具实际执行前拦截不合法调用：

- **Phase 门控**：`ALLOWED_TOOLS_BY_PHASE` 规定每个阶段可用工具集合（6 个阶段共 6 组集合）
- **PATCH 门控**：写文件需要三个条件同时满足 — 有复现证据 + 有定位候选 + phase 为 patch
- **定位一致性门控**：`write_file`/`edit_file` 的目标文件必须在 `localization_candidates` 中，除非提供 20 字以上的 `localization_override_reason`
- **search_graph 上限**：单次 run 最多 3 次

被拦截的调用返回 `ok=False`，`error.type="tool_policy_violation"`，模型收到可读的拒绝理由。

## 二、多工具调度与多轮循环

核心架构：**六阶段状态机** + **三层行为干预**。

### 阶段门控

**位置**：`tool_router.py` → `build_tools_for_state()`

每轮 LLM 调用前，根据 `AgentState` 动态裁剪可见工具列表：

- **understand**：`list_files`, `search_graph`, `grep`, `search_code`, `read_file`, `run_tests`
- **reproduce**：`grep`, `search_code`, `search_graph`, `run_tests`, `read_file`, `show_diff`
- **localize**：`grep`, `search_code`, `search_graph`, `read_file`, `python_repl`, `run_tests`
- **patch**：`grep`, `search_code`, `read_file`, `edit_file`, `write_file`, `show_diff`, `undo`, `run_tests`
- **verify**：`run_tests`, `show_diff`, `read_file`, `undo`
- **final**：`show_diff`

设计原则：LLM 可以自由选择工具，但不能选择不在阶段允许范围内的。

### 状态自动转移

**位置**：`tool_policy.py` → `next_phase_after_tool()`

每次工具调用后系统自动推进阶段，不依赖 LLM 声明：

```
run_tests + 有复现证据 + 有候选文件 → patch
只读操作 + 有候选文件 → patch
写入成功 → verify
show_diff 在 verify 中 → 保持 verify
```

### 并行调度

**位置**：`llm_agent.py` → `_partition_tool_batches()`

- **连续只读工具**（`search_code`, `grep`, `read_file`, `search_graph`）合并为一个 batch，`ThreadPoolExecutor` 并行执行
- **写工具**每个单独一个 batch，串行执行

不做复杂依赖分析，策略足够覆盖实际场景。

### 三层行为干预

| 层级 | 触发条件 | 机制 |
|------|---------|------|
| 读节流 | 连续 5 次 `read_file` 无写入 | 注入系统消息催促写入 |
| 预算升级 | 轮次达 75% 且 0 次写入 | `BUDGET_ESCALATION_TOOLS` 物理替换可见工具，只保留写+验证 |
| 反循环 | 连续 3 次同文件相似编辑 | 注入 "重新验证假设" 警告 |

设计哲学：软提醒 → 硬约束。

**预算升级的特殊处理**：升级消息拼入最后一条 user 消息尾部，不新增独立消息——避免打破 `assistant(tool_calls)` 与 `tool_result` 的配对关系。

### 写入后自动验证

**位置**：`llm_agent.py` → `run_immediate_auto_verification()`

写入成功后系统自动执行 4 步，不等待模型决策：

1. `show_diff` → 确认改动
2. `run_tests`（targeted scope，只跑失败节点）
3. `run_tests`（full scope，全量）
4. 失败则触发反射决策（可能 undo + 回退阶段）；全部通过则提前退出循环

### 反射决策

**位置**：`reflector.py` → `reflect_after_failed_verification()`

通过比较 `FailureSignature` 的 `output_hash` 判断根因：

- 失败哈希**未变** → `wrong_hypothesis`（改了跟 bug 无关的代码）
- 失败哈希**变了** → `partial_fix`（方向对，继续补）
- 改的文件不在候选列表 → `wrong_file`，应 undo

全部确定性逻辑，不消耗 LLM token。

## 三、工具结果太大怎么裁剪

五级递进压缩，从语义提取到硬截断。

### 1. 测试结果语义提取

**位置**：`run_tests.py` → `_build_failure_summary()`

不传原始输出，而是结构化提取：

- `failed_tests`：失败测试名
- `locations`：`[{path, line, error}]`
- `assertion_lines`：断言原文
- `exception`：异常类型 + 消息
- `possible_symbols`：从异常消息提取的符号名
- `output_excerpt`：最后 1200 字符原始输出（兜底）

### 2. 按工具类型的差异化压缩

**位置**：`tool_executor.py` → `summarize_for_model()`

每种工具不同策略：

| 工具 | 策略 |
|------|------|
| run_tests（成功） | 只留 `exit_code` + `duration_sec` |
| read_file | ≤20000 字符全量返回；>20000 字符只给前 2000 + 提示缩小范围 |
| search/grep | 最多 50 条匹配，告知截断数 |
| show_diff | 超过 6000 字符截断 + 提示用 read_file 查看 |
| write/edit（成功） | 丢弃写入 content，只留元数据 |
| edit_file（失败） | 保留 `similar_contexts` 帮模型定位正确 old_string |

### 3. 最终硬截断

**位置**：`tool_executor.py` → `_json_for_model()`

所有结果经过 `max_chars` 硬截断，最后一道防线。

### 4. 超大结果落盘（Spill）

**位置**：`llm_agent.py` → `_spill_large_tool_result()`

阈值 12000 字符。超过的结果写为文件 `step_NNN_toolname.json`，模型只收到：

```
[完整输出(NNN字符)已落盘至 step_NNN_toolname.json。以上为摘要预览。]
```

动机是保证审计链完整性。

### 5. 上下文窗口级压缩

**位置**：`llm_agent.py` → `_compress_messages_if_needed()` 和 `_microcompact_messages()`

- **微压缩**：对最后一条消息中超过阈值的 tool_result 做截断
- **窗口压缩**：当 token 估算超过 `context_window_tokens - reserve_tokens`，保留首条 + 最近 3 条消息，中间消息压为一行摘要

**配对保护**：压缩边界不会切在 `assistant(tool_calls)` 与其 `tool_result` 之间，否则严格校验的 API 会报 400。

## 关键文件索引

| `app/agent/llm_agent.py` | 主循环、并行调度、行为干预、spill、上下文压缩 |

| `app/tools/common.py` | 路径解析、文本文件识别 |
