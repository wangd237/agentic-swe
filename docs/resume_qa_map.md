## 1. 项目概述 → 追问与应答

### 📌 简历原文

> 面向真实代码仓库的 LLM Coding Agent，将 bug 修复拆解为 Understand → Reproduce → Localize → Patch → Verify → Final 六阶段，通过 Phase Gate、Tool Policy、Verification Quality Layer 等确定性组件约束 LLM 的开放行为，确保每步操作有据可依、结果可审计。覆盖 132 条 semi-real issue 与 10 个 SWE-bench Lite 任务，**官方判定 resolved 4/8**，真实 GitHub issue **4/5 修复语义与官方 fix commit 一致**，374 条回归测试全覆盖。

### 🔍 面试官视角：概述部分会触发的问题

#### Q0.1：「什么叫确定性组件？和 prompt 约束有什么区别？」

**面试官预设**：很多候选人会用 prompt 做行为约束（"请在修改前先运行测试"），你能说出为什么不够吗？

**标准回答**：

> Prompt 是**概率性建议**——你告诉 Agent "请先复现 bug 再改代码"，但 Agent 可以选择忽略。确定性组件是**物理拦截**——tool policy 在 UNDERSTAND 阶段直接禁止写入工具出现在工具列表里，Agent 连这个工具的 schema 都看不到，更谈不上调用。
>
> 这不是「信任模型」和「不信任模型」的区别，是编译器 type system 和代码规范的区别。规范告诉程序员"不要用未初始化的变量"，type system 让这种代码直接编译不过。我在做 agent 层的 type system。

**补充弹药（如果面试官追问"有证据吗"）**：

> click#3449 这个任务里，Agent 连续 3 次 run 收到提示式告警「你已探索过多，请总结并写 patch」——每次都无视，继续读代码读到轮次耗尽。换成硬约束（工具列表收窄至只保留写/验证工具）后，Agent 在拦截点转向合法路径，第 5 次 run 成功产出 patch，修复语义与官方 click 8.4.1 fix commit 同构。提示改变不了行为，约束可以。

#### Q0.2：「六阶段怎么流转的？阶段推进谁决定的？」

**标准回答**：

> 六阶段是证据驱动流转，不是时间驱动。每个工具执行完后，系统自动检查 Agent 的当前状态：有复现证据 + 定位候选非空 → 自动推进到 PATCH，全量测试通过 → 自动推进到 FINAL。关键设计是**自动推进**——不需要 Agent 主动说"我准备好了"，系统检查客观条件满足就自动放行。反过来也一样，条件不满足就留在当前阶段，Agent 说「我已经理解了」没用。

**可能追问**：「如果任务有设计讨论性质的 issue，Agent 永远找不到测试可跑，不就死锁了吗？」

> 问得好，这是真实场景下的边界情况。最初的状态机隐含假设「总有测试可跑」——真实仓库里不成立。修复方案是增加 fallback：只要定位候选非空（有明确的待修改文件），即使没有复现证据也允许进 PATCH。弹性在前、底线在后——不能因为没测试就不修，但必须知道修哪个文件再动手。

**证据**：War Story 4（phase deadlock 修复）

#### Q0.3：「SWE-bench Lite 4/8，真实 GitHub 4/5，这两个口径什么区别？」

**标准回答**：

> SWE-bench Lite 用官方 Docker harness 判定——必须所有测试通过才算 resolved，这是最严格的口径。真实 GitHub issue 的口径是「修复语义与官方 fix commit 一致」——我修复的代码逻辑和官方维护者后来提交的修复是同构的。后者没有标准化的自动判定，是我手动对比验证的。
>
> 两个口径互补：SWE-bench 提供标准化、可复现的量化基准，真实 issue 证明系统在处理「没见过"标准答案"的任务」时的泛化能力。

**防坑提示**：不要过度强调 4/8 这个数字本身，引导到单条任务的深度分析（click#3449 五次 run、pydicom-1139 翻盘）。

#### Q0.4：「132 条 semi-real issue 是什么？和 SWE-bench 什么关系？」

**标准回答**：

> Semi-real issue 是从真实 GitHub issue 中提取的最简复现场景——保留了原 issue 的核心逻辑和测试失败，但剥离了复杂的环境依赖。132 条任务覆盖 9 个开源库（rich / jinja / click / jsonschema / packaging / tomlkit / watchfiles / anyio / dateutil），用作 Agent 行为验证的日常基准。

#### Q1.1：「证据驱动流转——什么算证据？怎么判定的？」

**标准回答**：

> 两类硬证据。复现证据：Agent 调用了 run_tests 且返回了失败（失败签名非空）。定位候选：Agent 通过代码定位模块的评分或自己搜索命中了具体文件，被加入 Agent 状态的候选文件列表。
>
> 判定逻辑是：每次工具执行完，系统自动检查 Agent 状态——是否有复现证据、候选文件列表是否非空。两个条件都满足 → 推进到 PATCH。全量测试通过且改动已验证 → 推进到 FINAL。
>
> 注意这里的「硬」是指——判定是布尔值而非置信度，不依赖 LLM 的判断。

---

#### Q1.2：「Token -39% 怎么来的？有对照组吗？」

**标准回答**：

> task_010 用同一任务、同一模型、同一 prompt 跑了对比——baseline 暴露全部 11 个工具，干预组按阶段裁剪（UNDERSTAND 阶段只暴露读文件和搜索工具，屏蔽写入工具）。对比结果：baseline 30,510 tokens / 7 次 LLM 调用，干预组 18,553 tokens / 5 次 LLM 调用，成功率相同。
>
> 但我必须补充——这个单任务验证后来被证明有欺骗性。扩展到 5 个任务后，2/5 的 token 反升了。规律是反升的两个恰好 LLM 调用多了 1 轮——省 schema 是小头，多一轮完整上下文重发是大头。这直接导致了后续的设计转向：把节省方向从「省 schema」改为「省轮次」。

**证据**：War Story 3（token 优化收益被抵消）

---

#### Q1.3：「四道规则分别是什么？怎么实现物理拦截的？」

**标准回答**：

> 每轮 LLM 返回工具调用请求后，门禁检查逻辑按顺序走四道：
>
> ① **阶段白名单**：当前请求的工具是否在「当前阶段允许使用的工具列表」中。不在 → 直接拒绝，模型收不到工具执行结果。
> ② **PATCH Gate**：如果请求的是写入工具，检查是否已有复现证据且候选文件列表非空。任一不满足 → 拒。
> ③ **写入门禁**：写入的目标文件必须在候选文件列表中。不在 → 拒。这防止了「Agent 凭直觉改了一个没分析过的文件」。
> ④ **diff-before-tests**：维护两个计数器——工作区写入次数和 diff 观察次数。两者不相等时禁止跑测试——堵死了「先跑测试 → 又改文件 → 没重验 → 标成功」的时序漏洞。

**可能追问**：「第四道门这个代数校验，是你原创的吗？」

> 这个想法来自分布式系统的 epoch/version 校验，但在 Agent 上下文中是我自己实现的。本质是一个简单的不变式：在每次写入增加了版本号后，必须通过查看 diff 观察一次，才能跑测试。不需要 LLM 记住"我改完文件了没看 diff"，代码帮你记住。

---

#### Q1.4：「预算硬约束是怎么升级的？从提示到硬约束」

**标准回答**：

> 最初的实现是提示式的——预算监控检测到「当前轮次超过 75% 上限且零写入」时，在下一轮的 system prompt 里注入提醒。click#3449 的 Run 2 证明这个策略无效——Agent 收到提示后继续读代码，没有行为变化。
>
> 于是升级为硬约束：不再提示，而是直接把可选工具列表从 11 个收窄到 3 个（edit_file / write_file / run_tests），物理上只能写或验证。Run 5 验证了硬约束的有效性——Agent 在拦截点上切换到合法路径，成功完成修复。

**面试金句**：*「提示是希望他听话，硬约束是让他只能做对的事。」*

---

#### Q1.5：「click#3449 的五次 run，详细讲讲？」

**这是面试中最核心的叙事线**。面试官问到这个意味着他对你的工程能力产生了真正的兴趣。

**标准回答（2 分钟版）**：

> click#3449 是 click 库的一个真实 issue——`color=False` 时 ANSI 控制码泄漏到输出里。我们跑了 5 次：
>
> | Run | 策略 | 结果 |
> |---|---|---|
> | 1 | 无干预 | 探索 16 轮耗尽，0 patch |
> | 2 | 提示式告警 | 同样探索到死——Agent 无视提示 |
> | 3 | 硬约束（4 工具） | 模型被拦截后连续空响应——**当时误判为罢工** |
> | 4 | 硬约束 + python_repl | 同样空响应 |
> | 5 | 硬约束 + max_tokens 修复 | **success，1 patch，语义与 click 8.4.1 同构** |
>
> Run 3/4 的「罢工」其实是 max_tokens 截断——reasoning 模型把思考链算在 8000 token 上限里，思考烧完上限后模型还没来得及输出文字就被截断了。API 返回的 finish_reason=length 暴露了这个问题（如果是主动停止会是 stop）。修完 max_tokens 配置后，Run 5 成功了。
>
> 这个案例的价值：**表象（空响应）≠ 根因（截断），提示无效 ≠ 方向不对，硬约束有效只是被另一个 bug 掩盖了。** 五次 run 的完整弧线证明了从「拍脑袋改 prompt」到「观测驱动定位根因」的方法论转变。

**如果面试官追问「扣细节」**：

> - 「怎么发现 max_tokens 是根因？」→ 逐轮 token 分解，发现 completion_tokens 精确等于 8000
> - 「为什么 Run 3/4 不检查 finish_reason？」→ 这是当时的盲点——我们只看了输出内容，没看 API 返回的结束原因字段。修完后 finish_reason 被加入监控
> - 「硬约束到底做了什么？」→ 工具列表从全部 11 个收窄到仅保留 edit_file / write_file / run_tests / show_diff / undo，物理上禁止读文件和搜索

**证据**：War Story 11（max_tokens）

## 3. Bullet ② — 确定性反思与自动验证

### 📌 简历原文

> **确定性反思与自动验证：**实现 130 行纯函数 Reflector，**零 LLM 调用**完成失败签名对比与 undo/保留决策；写入后 Runtime 自动执行三级验证链（show\_diff → targeted tests → full tests），结果同轮回喂，消除验证决策的额外 LLM 轮次（**5 任务平均 Token -27.4%**）。

### 🔍 埋点拆解与追问

| # | 钩子 | 面试官第一反应 | 追问方向 |
|---|---|---|---|
| 1 | 「130 行纯函数」 | "为什么不拆文件？为什么这么小？" | 设计决策 |
| 2 | 「零 LLM 调用」 | "为什么不交给 LLM 做反思？" | 架构哲学、与主流做法的对比 |
| 3 | 「失败签名对比」 | "怎么对比的？怎么区分 unchanged/changed？" | 技术实现 |
| 4 | 「三级验证链同轮回喂」 | "怎么做到不额外消耗轮次的？" | 实现原理 |

---

#### Q2.1：「130 行纯函数——为什么不拆成多个文件？为什么这么小？」

**标准回答**：

> 反思器的职责很窄：输入是 Agent 的当前状态（patch 信息、失败签名、候选文件列表），输出是一个决策（undo+回退 / 保留+继续）。所有决策路径都在一个 5 分支的 if-elif 树里——拆成多个文件反而增加认知负担。
>
> 至于为什么这么小——因为所有判断都是确定性的。失败签名对比就是哈希比较，wrong_file 判定就是集合运算（改了什么文件 vs 定位候选是什么），没有 LLM 调用、没有 I/O、没有异步。130 行里还有 20 行是注释。**好代码不是行数多，是恰好够用。**

---

#### Q2.2：「零 LLM 调用——为什么不交给 LLM 做反思？」⭐ 高概率被问

**这是简历上最强的钩子之一。**

**标准回答**：

> 业界常见做法是把反思写成 prompt：「你写的 patch 测试失败了，请分析原因并决定下一步」。这种做法有三个问题：**不可测试**（同一个输入 LLM 可能返回不同输出）、**不可审计**（不知道模型为什么做了这个决定）、**烧 token**（又一次完整上下文重发）。
>
> 我选择纯函数是因为反思的决策空间其实很小——只有 5 种情况：

| 条件 | 判定 | 行为 |
|---|---|---|
| 改了候选之外的文件 | wrong_file | undo + 回 localize |
| 改动文件最高 confidence < 0.4 | low_confidence | undo + 回 localize |
| 改动文件数超过限制 | overfit | undo + 回 localize |
| 失败签名不变 | wrong_hypothesis | 不回滚 + 回 localize |
| 失败签名变化 | partial_fix | **保留 patch + 继续 PATCH** |

> 最后一种情况是最关键的设计：失败签名变了但没完全修好时，**不回滚**——因为失败签名变化意味着补丁产生了影响，方向正确。这区别于"失败签名没变 = 改错文件了 = 应该回滚"。这个判断如果交给 LLM，它可能会把两种情况都判定为"失败，重来"。

**面试金句**：*「当你发现决策空间只有 5 种情况的时候，写 if-else 是比调 LLM 更好的方案。」*

---

#### Q2.3：「失败签名对比具体是怎么做的？」

**标准回答**：

> 失败签名是一个哈希值，来自 run_tests 返回的失败测试信息——把失败测试名、断言位置、异常类型组合后取哈希。写入 patch 后跑 targeted tests，对比修复前和修复后的签名。
>
> - **签名不变**：修复后的签名哈希和修复前完全相同 → 补丁没有改变任何失败测试的行为 → 改错了
> - **签名变化**：哈希不同 → 至少有一个测试的失败表现变了 → 补丁产生了影响
> - **出现新失败**：之前没失败的测试现在失败了 → overfit（修了一个 bug 引入了新的）

---

#### Q2.4：「三级验证链同轮回喂——怎么实现不消耗额外轮次的？」

**标准回答**：

> 写入工具执行成功后，在**同一轮 agent loop 内**，系统串联执行三个验证步骤：
> 1. show_diff — 查看当前工作区变更
> 2. targeted run_tests — 只跑之前失败过的测试（符号级定位，快）
> 3. full run_tests — 跑完整测试套件
>
> 三个步骤的结果打包成同一条消息回喂给 LLM。之前的设计是：写入完成后返回一轮 → LLM 决定 show_diff → 再一轮 → LLM 决定跑 targeted tests → 再一轮 → LLM 决定跑 full tests。每轮都要把完整历史重发给 LLM。
>
> 下沉到 runtime 后，三个步骤变成零轮次——Agent 不需要"决定"做这些事，系统自动做完并把结果喂给它。

**可能追问**：「如果 Agent 在写入后还想继续读文件怎么办？」

> 依然可以读。自动验证在写入后同步执行——跑完验证后本轮才结束，下一轮 Agent 拿到验证结果 + 上下文后可以正常发起新的工具调用。自动验证不阻塞后续操作，只是把原本需要 Agent 手动发起的验证步骤前置化、自动化了。

---

#### Q2.5：「Token -27.4% 和前面的 -39% 什么关系？」

**标准回答**：

> -39% 来自 Schema 裁剪，在 task_010 单任务上测的。后来我做了扩展验证——在 5 个任务上测自动验证优化，发现均值是 -27.4%。
>
> 这两个数字对应两个不同的优化方向，而且它们之间有一个重要的教训：
> - **Schema 裁剪省的是每轮发送的 tool definition**（固定开销，约 3-5K tokens）
> - **自动验证省的是轮次**（每少一轮就少一次完整上下文重发，约 15-50K tokens）
>
> 我一开始以为 Schema 裁剪效果很好（单任务验证 -39%），后来扩展到 5 个任务发现 2/5 反升——因为 Schema 裁剪没有减少轮次，如果 Agent 因此多探索了一轮，多出的上下文重发把 schema 节省全吃掉了。所以自动验证（省轮次）比 Schema 裁剪（省 schema）更稳定、效果更大。

## 4. Bullet ③ — 验证质量分层

### 📌 简历原文

> **验证质量分层：**构建四级验证强度体系（Missing / Weak / Local Smoke / Full Verification），模型自称成功但证据不足时 **系统强制降级**——验证结论由代码判定，非模型自报，防止 Agent 将弱验证包装为可信成功。

### 🔍 埋点拆解与追问

| # | 钩子 | 面试官第一反应 | 追问方向 |
|---|---|---|---|
| 1 | 「四级验证强度」 | "哪四级？怎么定义的？" | 分级标准 |
| 2 | 「系统强制降级」 | "什么情况触发降级？有案例吗？" | 降级逻辑 + pydicom |
| 3 | 「验证结论由代码判定，非模型自报」 | "模型怎么会自称成功？" | Agent 的行为模式 |
| 4 | 「防止弱验证包装为可信成功」 | "这是常见问题吗？" | 行业现状 + 你的贡献 |

---

#### Q3.1：「四级验证强度分别是什么？怎么定义的？」

**标准回答**：

| 级别 | 条件 | 含义 |
|---|---|---|
| **Missing** | 无 patch + 无测试证据 | 什么都没做，直接拒绝 |
| **Weak / Static** | 有 patch 但未运行测试，仅静态分析或模型自称 | 不可接受 |
| **Local Smoke** | patch + 本地全量测试通过 | 可信但不等于官方通过 |
| **Full Verification** | patch + 修复前有失败证据 + 修复后全量通过 | 最强证据 |

> 升级逻辑是累积的——每多一步验证证据，等级就升一级。但关键不在于升级，在于**降级**。即使 Agent 已经走到了最高级，如果系统检测到证据链断裂（比如修复后测试的结果文件丢失），它会降级——这是防御性设计。

---

#### Q3.2：「系统强制降级——什么情况触发？有具体案例吗？」⭐ 高概率被问

**标准回答**：

> 三个触发条件：
> 1. **Agent 声称 success 但没有 full test 证据** — 比如 Agent 只跑了 targeted tests 就说修好了 → 降级
> 2. **SWE-bench Lite 任务本地测试全过** — 即使本地 full tests 全部通过，系统自动降级并标记「缺少官方 harness 验证」
> 3. **证据质量综合评估为 weak 或 partial** — 验证模块综合评估后降级
>
> 最好的验证案例是 pydicom-1139：本地容器里同一批测试全部通过，Agent 认为修好了。但用 SWE-bench 官方 Docker harness 跑，被判定为 unresolved（regression）。系统的验证质量分层在这里得到验证——标记为 local_smoke_success + 证据不完整 + 缺少官方验证，没有错误地声称 resolved。

---

#### Q3.3：「模型怎么会自称 success？」

**标准回答**：

> Agent 的 prompt 设计中有「完成修复后声明 final_answer」的机制。但 LLM 的行为是不可靠的——它可能在看到 targeted tests 通过后就觉得自己修好了，在没跑 full tests 的情况下直接声明 success。
>
> 另一个常见场景是「本来就没坏」——Agent 写了一个空 patch 或者改了一个无效行，然后发现 targeted tests 本来就能过，就声称 success。验证质量分层要求修复前失败证据 + 修复后全量通过两个条件同时满足，堵死了这种假阳性。

---

#### Q3.4：「防止弱验证包装为可信成功——这是你发现的行业问题还是你自己的项目问题？」

**标准回答**：

> 两者都是。在构建这个 Agent 的过程中，我读了很多 SWE-bench 的评测报告，发现一个常见模式——很多系统把「本地测试通过」报告为「resolved」，但实际上用官方 harness 重跑后通不过。这不是作弊，是验证口径不一致。
>
> 我自己的项目里也遇到了同样的陷阱——pydicom-1139。所以我设计了验证质量分层把这个问题制度化了：不是靠人的诚信来区分本地通过和官方通过，而是让系统自动标记，任何人都能从运行结果文件里看到证据质量字段。

## 5. Bullet ④ — 上下文工程与评测体系

### 📌 简历原文

> **上下文工程与评测体系：**以 API 实测 token 用量为锚点驱动上下文压缩判定，替代静态字符阈值，校准后同等任务零错误压缩；测试失败信息结构化提取（断言位置 / 异常类型 / 符号名），无需模型读取完整日志即可定位根因。frozen\_40 连续 **72+ 策略版本零回归**，全部运行证据随仓库分发、逐条可审计。

### 🔍 埋点拆解与追问

| # | 钩子 | 面试官第一反应 | 追问方向 |
|---|---|---|---|
| 1 | 「API 实测 token 为锚点」 | "原来用的什么？为什么不好？" | 校准过程 |
| 2 | 「校准后零错误压缩」 | "校准前什么情况？" | 量化对比 |
| 3 | 「结构化提取 failure_summary」 | "提取了什么？效果如何？" | 实现 + 收益 |
| 4 | 「72+ 版本零回归」 | "怎么保证的？frozen set 是什么？" | 评测方法论 |
| 5 | 「全部运行证据随仓库分发」 | "都有哪些产物？怎么审计？" | 可审计设计 |

---

#### Q4.1：「用 API 实测 token 替代字符阈值——原来用的什么？为什么不好？」

**标准回答**：

> 原来用的是一个固定字符阈值——当消息历史的字符数超过 80,000 字符时触发压缩。这个阈值是 6 月 15 日定的，之后两个月从来没验证过。
>
> 8 月底我建了一个观测管道，收集了 3 个任务 46 次 API 调用的实测 token 数。两个关键发现：
> 1. 稳态 chars/token 比值是 2.45，偏差 ±24%——换句话说，用字符数估算 token 数本身就不可靠
> 2. 我用的是 deepseek-v4-flash，窗口是 **1M tokens**，不是我以为的 64K。80K chars ≈ 37K tokens ≈ 窗口的 3.7%
>
> 结论是颠覆性的：**压缩在长任务里从来都不必要。** 每次压缩都在丢弃不该丢弃的上下文，纯粹被一个从未校准的阈值人为触发。

**面试金句**：*「拍脑袋的阈值不会自己变对，观测才会告诉你真相。我从 6 月到 8 月都不知道自己在浪费上下文。」*

---

#### Q4.2：「校准后做了什么改动？效果如何？」

**标准回答**：

> 三件事：
> 1. 把压缩判定从「字符数超过固定阈值」改为「估算 token 数超过模型窗口减预留量」，估算用上次 API 返回的实际 prompt_tokens 做锚点
> 2. 无锚点时（程序刚启动、还没调过 API）用字符数除以 2.5 做保守估算
> 3. 加了配对保护——压缩边界不能切在 assistant(tool_calls) 和 tool_result 之间（这会破坏 OpenAI 消息格式）
>
> 校准后用 marshmallow_1343 做对比测试：旧方案压缩 1 次，新方案 0 次。任务上下文全程 38.5K tokens（占窗口 3.9%），PATCH 阶段的完整历史一直保留到任务结束。

**证据**：War Story 9

---

#### Q4.3：「结构化提取 failure_summary——提取了什么？效果如何？」

**标准回答**：

> run_tests 工具在返回结果前，解析 pytest 的输出，提取四个关键信息：
> - 哪些测试失败了
> - 断言位置（文件 + 行号）
> - 异常类型（AttributeError / AssertionError 等）
> - 从异常消息和断言中提取的可能相关的变量/函数名
>
> 效果：Agent 不需要读完整的 pytest 输出（可能是几千行），只看结构化摘要就能知道"哪个测试挂了、在哪挂的、大概和什么有关"。拿到这个摘要后，Agent 的下一步一般是自动搜索相关符号——这个行为被合并到了 run_tests 工具内部，不需要 Agent 额外发起。
>
> 这是「在工具层解决问题」的思路——不是让 Agent 更聪明，是让工具返回的信息更精准。

---

#### Q4.4：「72+ 策略版本零回归——怎么保证的？frozen set 是什么？」⭐ 高概率被问

**标准回答**：

> Frozen set 是从 132 条 semi-real task 中抽取的固定评测集——frozen_40 包含 40 条任务，frozen_15 包含 15 条。它们只增不减、永不修改（新增任务可以加入但不替换已有任务）。
>
> 每次改了策略或 Agent 逻辑后，用同一份 frozen set 重新跑并对结果做 diff。如果新增了失败——就是回归。回归必须被修复或承认（记录为 known regression，明确根因和时间）。
>
> frozen_40 我已经连续 72+ 个策略版本跑下来，零回归。这是数据结构化的纪律——不是靠记忆判断"这次改动应该不会影响之前的任务"，而是靠自动化回归每次告诉你。
>
> 374 条 pytest 单元测试覆盖的是组件级别，frozen set 覆盖的是端到端行为级别——两层互补。

**可能追问**：「Frozen set 和 SWE-bench 的关系？」

> Frozen set 是内部迭代用的复现性基准，SWE-bench 是对外可比的标准基准。一个用于高频迭代（几分钟），一个用于里程碑验证（小时级）。

---

#### Q4.5：「运行证据都有什么？怎么审计？」

**标准回答**：

> 每次 run 产出四个文件：
> - trace.json：每一轮的工具调用、参数、返回值、token 消耗、Agent 状态快照
> - result.json：最终状态、验证证据、验证报告、已接受的状态
> - patch.diff：实际的代码变更
> - summary.md：人类可读的任务总结
>
> 审计的意思是：任何人（不一定是我）拿到这四个文件 + 原始任务定义，可以独立复现判断——Agent 在每一步做了什么、为什么这么做、最终结论是否站得住脚。验证质量分层的证据等级和缺失证据字段让第三方不需要信任我，可以自己检查证据是否充分。

### QX.3：「主循环文件为什么有两千多行不拆？」

**标准回答**：

> 这是有意识的设计决策。agent loop 有 18 处干预点——预算升级注入、自动验证回喂、反思触发、阶段推进、上下文压缩——它们之间有严格的执行顺序。拆分会让这种顺序依赖变成隐式的状态传递，改代码时容易破坏顺序。
>
> 2500+ 行在一个文件里不漂亮，但顺序是正确的。而且项目已收敛——收敛期做大规模重构的风险不可接受。不是「没时间拆」，是「选择不拆」。面试时能把选择说清楚，比行数好看更重要。

---

### QX.4：「你最大的收获或教训是什么？」

**标准回答**（推荐讲 search_graph 三连 bug）：

> 最重要的教训是归因方法论——很多问题的表象是指向模型的，但根因在代码里。
>
> 我花了两天做了 4 轮 prompt 干预想让 Agent 用 search_graph 工具，最后发现是三个代码 bug——其中一个字段名不匹配，工具返回的字段叫 `results`，读取时用的是 `matches`。模型看到的一直是空数组。82 个单元测试全过，因为测试只覆盖了「调用后返回什么」，没覆盖「模型视角看到什么」。
>
> 从那之后，我给每个新工具加了从模型视角的端到端验证——不是测代码对不对，是测模型看到的东西是不是你认为它看到的东西。

**证据**：War Story 1

---

### QX.5：「如果你重新做这个项目，会怎么设计？」

**标准回答**：

> 三个改变：
> 1. 第一天就用 token 预算而非字符估算——避免两个月的无效压缩
> 2. 单任务验证结果不急于推广——token 优化那次早做扩展验证能少走两周弯路
> 3. 每个改进走完「发现→归因→修复→重跑→数字对比」的完整闭环再开始下一个，而不是发现一个写篇文档就放一边

---

### QX.6：「这个项目下一步做什么？」

**标准回答**：

> 项目已收敛，面试准备阶段保持现状。但如果继续做，三个方向：
> 1. 重叠读检测——55%+ 的文件读取调用是重复的，拦截可以省 token
> 2. 读操作节流——对称于已有的写侧反循环检测
> 3. 预算升级从 hint 改为硬约束——click#3449 已经有证据支持
>
> 核心思路是「关闭已知问题」而非「加新功能」。
