## 1. 现状诊断

### 1.1 你的 Agent 现在怎么"知道"自己改对了

```
Understand → Reproduce → Localize → Patch → Verify → Final
                                              ↑
                                          show_diff
                                              ↓
                                       targeted tests (3 优先级)
                                              ↓
                                       full tests
                                              ↓
                                       Reflector (纯函数)
```

**判定逻辑**：
- show_diff：Agent 看完 diff 后**自己**说"改对了"——**自报**
- targeted tests：跑修改文件相关的测试，**过了 = 改对了**
- full tests：跑全量测试，**过了 = 改对了**
- Reflector：纯函数对比"失败签名 vs 已知失败模式"，决定 undo / 保留

### 1.2 这个判定链的 3 个结构性漏洞

#### 漏洞 1：自报不可信
> "Agent 改完代码后自己说'我改对了'"——这是**模型自评**，不是系统判定。

v2 面试官 push：
- "你 verify 阶段 model 自报成功但证据不足，你是怎么发现的？"——你答："靠 targeted tests + full tests 兜底"
- 但如果**测试覆盖不到**呢？

#### 漏洞 2：测试覆盖率天花板
> "测试覆盖了 60% 的代码路径，剩下 40% Agent 改错了也发现不了。"

v2 面试官 push：
- "pydicom-1139 那次翻盘，Reflector 看到了吗？"——你答："纯函数 Reflector 只能判断 wrong_file / 失败签名，但 pass-to-pass 回归（测试过了但行为变了）它看不到"
- "测试覆盖率 60% 的项目，你 Agent 怎么知道改得对不对？"——你**没正面回答**

#### 漏洞 3：定位质量无法验证
> "Agent 在 Localize 阶段说'问题在 A 文件第 23 行'——但系统**没法判断这个判断对不对**。"

v2 面试官 push：
- "你区分了'有定位'和'定位正确'吗？"——你答："没区分，`can_patch()` 只要求 candidates 非空"
- "这是 Phase Gate 的设计漏洞吗？"——你答："是——把定位验证从 REPRODUCE 前移到了 PATCH 内"
- "那 PATCH 阶段的自动验证怎么知道定位是对的？"——你答："靠 show_diff + tests 立即验证"

**这个回答**等于承认：**你的 Agent 是在"先改再验"，不是"先验定位再改"**——这本身是设计权衡，但**你之前没清晰表述过这个 trade-off**。

### 1.3 面试官的真实 push 路径

```
v1 面试官：测试覆盖率低时 Agent 怎么知道改对？
   ↓
v2 面试官追问：pass-to-pass 回归 Reflector 看不到
   ↓
v2 面试官追问：定位是幻觉怎么办
   ↓
结论：3 个漏洞 = 1 个核心问题：Agent 自我纠错能力 = 强依赖测试覆盖
```

**核心问题**：你的 Agent **没有"独立于测试"的自我纠错能力**——所有判定都建立在"测试覆盖"这个外部条件上。

## 2. 目标（做完这块你能回答什么）

补完后，**任何**面试官问"Agent 怎么知道自己改对了"你都能答：

> "我的系统有 3 层判定，从弱到强：
>
> 1. **模型自评**（Verify 阶段 model 自报）—— 不可信
> 2. **测试覆盖**（targeted + full tests）—— 强依赖覆盖率
> 3. **系统级补判**（test 之外的客观校验）—— 这是我承认的弱项
>
> 系统级补判我有 3 种候选方法，但**当前实现只用了 1 个的简化版**：
>
> | 方法 | 原理 | 我的项目当前状态 |
> |---|---|---|
> | **A. LLM 复审** | 第二个独立 LLM 复审 | ❌ 没做 |
> | **B. targeted tests 反查** | 让 Agent 写最小复现 | ⚠️ 简化版（只跑已有测试，不写新测试）|
> | **C. git blame 反向验证** | 历史修改者视角 | ❌ 没做 |
>
> Trade-off：
> - A 准但贵（每次 +1 次 LLM 调用）
> - B 中等准但要小心"测试本身写错"
> - C 只对老项目有效
>
> 为什么我没全做？因为**测试覆盖率达到 80%+ 时，3 层足够**；测试覆盖低时，3 个都做了也只能补一部分——**这是工程 trade-off，不是技术不能**。
>
> 实际补救方案：v4 我会**加 LLM 复审 + 置信度阈值**——低置信度 case 主动触发二阶段评审。"

——这才是 P7 看的**工程成熟度**：知道自己能力的边界、知道 trade-off、知道下一步怎么补。

## 3. 实施步骤

### 3.1 写方法论文档（2-3 小时）

**文档结构**（直接落 `docs/agent_self_correction.md`）：

```markdown
# Agent 自我纠错能力 · 设计与边界

## 1. 问题定义
Agent 怎么知道"我刚才定位的问题是真的问题、不是幻觉"？
Agent 怎么知道"我刚才改的代码是对的、不是测试碰巧过"？

## 2. 当前实现的 3 层判定
### 2.1 模型自评（Verify 阶段）
- 原理：Agent 改完代码后读自己的 diff + 测试输出，自报"成功/失败"
- 漏洞：模型偏见、模型对自己答案的高估
- 反例：v2 模拟面试组 3 抓到的"Agent 看到测试通过就自报成功，但 pass-to-pass 回归"

### 2.2 测试覆盖（targeted + full tests）
- 原理：跑相关测试，通过 = 改对了
- 漏洞：测试覆盖率天花板
- 反例：pydicom-1139 翻盘，targeted tests 过了但语义不对
- 数据：我们项目测试覆盖率约 75%，剩余 25% 路径 Agent 改错也发现不了

### 2.3 失败签名对比（Reflector）
- 原理：纯函数对比 "当前失败签名 vs 已知失败模式"
- 能力边界：能判 wrong_file / 失败类型，不能判 pass-to-pass
- 漏洞：纯函数 = 看不到语义变化
- 反例：Agent 改了逻辑但 targeted tests 没覆盖这部分，full tests 也过——Reflector 看到的是"无失败"= "成功"

## 3. 3 种补判方法（候选）

### 3.1 LLM 复审
- 原理：第二个独立 LLM 读 Agent 的 diff + 测试输出 + issue 描述，独立判断"改对了吗"
- 适用：复杂问题、需要深度语义推理
- 反例：两个 LLM 可能共享训练偏见，共识不等于正确
- 成本：每次任务 +1 次 LLM 调用（按 deepseek-chat 约 ¥0.01-0.05）
- 准确度估计：80-90%（在 SWE-bench 上我没实测）

### 3.2 targeted tests 反查
- 原理：让 Agent **写一个新测试**去验证"问题确实在它说的那个地方"
- 适用：能写最小复现的问题
- 反例：测试本身可能写错（"测试错误地通过"是经典反例）
- 成本：+1 次 LLM 调用 + 跑测试时间
- 准确度估计：70-85%

### 3.3 git blame 反向验证
- 原理：用 git history 看"这块代码上次被改动的 issue 是不是和当前 issue 描述对得上"
- 适用：长期维护的项目
- 反例：新写的代码没历史；agent 改的代码本身没历史
- 成本：纯本地操作，几乎无成本
- 准确度估计：40-60%（弱信号，需要结合其他判定）

## 4. 当前项目的 trade-off
### 4.1 为什么只用了简化版 targeted tests？
- 完整版（让 Agent 写新测试）= +1 次 LLM 调用 × 109 题 = 100+ 次调用 ≈ ¥5-10
- 准确度提升估计：5-10pp
- ROI 不划算：相比继续调 Phase Gate 优化更值得

### 4.2 什么时候必须升级到完整版？
- 测试覆盖率 < 50% 的项目
- 改的是核心业务代码（不是边界 case）
- 修改的代码有跨模块依赖

### 4.3 我的项目实际策略
- **当前**：只跑现有 targeted tests + full tests + Reflector（纯函数）
- **未做**：LLM 复审 / 让 Agent 写测试 / git blame 验证
- **理由**：测试覆盖率 75% + Reflector 已能覆盖大部分失败模式
- **v4 计划**：加 "低置信度 LLM 复审"——当 Reflector 判 "high confidence local_smoke" 时不触发，判 "low confidence" 时触发一次 LLM 复审

## 5. 反例汇总
| 反例 | 当前能否发现 | 应该用哪种补判 |
|---|---|---|
| Agent 改错文件 | ✅ Reflector (wrong_file) | 无需补 |
| 改了文件但改错逻辑 | ⚠️ 仅当 targeted tests 覆盖 | B (写最小复现) |
| 测试过了但行为变（pass-to-pass） | ❌ | A (LLM 复审) |
| Agent 改了对的地方但没改根因 | ❌ | A (LLM 复审) |
| 改的代码引入新 bug | ⚠️ 仅当 full tests 覆盖 | B + 静态分析 |

## 6. 结论
- 当前 Agent 的自我纠错能力**强依赖测试覆盖率**
- 3 种补判方法都有 trade-off，没有银弹
- v4 的具体方案：低置信度触发 LLM 复审
- **这是工程 trade-off，不是技术不能**
```

## 5. 关键反例 / 坑

### 5.1 不要踩的坑

1. **不要给 Reflector 套"完美"帽子**——它就是纯函数，只做失败签名对比，**说不擅长的就是 pass-to-pass**
2. **不要把"测试通过"当"改对了"**——这是常识，但面试官会专门 push 这个
3. **不要假装 v4 已经实现了 LLM 复审**——你只是"计划"，说"已实现"会翻车
4. **不要忽视 git blame 方法**——它虽然弱，但成本几乎为 0，可以作为兜底层
5. **不要在简历上写"自我纠错"**——太抽象，面试官会问"怎么纠错"，然后你答不上来

### 5.2 必须做的检查

1. **3 种补判方法的成本估算**——必须能脱口而出"LLM 复审每次 +¥0.01-0.05"
2. **测试覆盖率数字**——必须知道你的项目测试覆盖率（75% 是估的，真实数字要去跑 coverage 工具）
3. **pass-to-pass 反例**——必须准备至少 1 个具体 case（pydicom-1139 是天然的）
4. **Reflector 看不到的边界**——能列出 3 个具体场景（pass-to-pass / 改对文件但改错逻辑 / 改错根因）
